# IEEE 29148:2018 — Quality Standard for Software Requirements

Стандарт валидации ТЗ по IEEE 29148:2018. Оценивает полноту, точность и реализуемость требований к ПО.

## Validation Contract

```yaml
input:
  - spec content (markdown)
  - .ai/ARCHITECTURE.md (контекст)

output:
  score: 0-100
  pass: score ≥ 85
  feedback: список проваленных критериев с рекомендациями
```

## Assessment Framework

Порог: **≥85 баллов из 100**. Каждый критерий: 0 (нет) / 3 (частично) / 5 (полностью).

---

## Section 1: Individual Requirement Quality (40 pts)

8 атрибутов качества каждого отдельного требования (IEEE 29148:2018, Clause 5.2.4).

### Necessary (5 pts)

**Определение:** Требование определяет существенную возможность системы, без которой она теряет ценность.

**Что собрать:**
- Бизнес-цель, которую обслуживает требование
- Стейкхолдер-потребность, из которой оно вытекает
- Ценность для пользователя (что произойдёт без него)

**Как проверить:** Удалите требование из spec. Система теряет ценность? Если нет — оно не необходимо. Требование не должно быть продиктовано "хотелкой" — за ним стоит реальная потребность.

**Почему:** Ненужные требования раздувают scope, увеличивают затраты на реализацию, тестирование и поддержку без добавления ценности.

---

### Unambiguous (5 pts)

**Определение:** Требование допускает только одну интерпретацию.

**Что собрать:**
- Формулировку каждого требования
- Потенциально неоднозначные термины
- Глоссарий проектных терминов

**Как проверить:** Два инженера независимо интерпретируют требование — совпадут ли результаты? Ищите качественные прилагательные без метрик: "быстрый", "надёжный", "удобный" — красные флаги.

**Почему:** Неоднозначность — источник переделок. Разработчик реализует свою интерпретацию, заказчик ожидает другую. Стоимость исправления растёт экспоненциально с задержкой обнаружения.

---

### Complete (5 pts)

**Определение:** Все характеристики и ограничения описаны достаточно для реализации без дополнительных вопросов.

**Что собрать:**
- Предусловия и постусловия
- Входные и выходные данные (типы, форматы, диапазоны)
- Граничные случаи и error-сценарии
- Ограничения (производительность, совместимость, платформа)

**Как проверить:** Может ли разработчик реализовать требование, не задавая вопросов? Нет ли "и т.д." или "и прочее"? Каждый сценарий использования покрывается полностью?

**Почему:** Неполные требования заставляют разработчика угадывать недостающие детали. Угадывание = баги, несоответствие ожиданиям и переделки.

---

### Consistent (5 pts)

**Определение:** Требование не противоречит другим требованиям и системным ограничениям.

**Что собрать:**
- Все требования из spec
- Системные ограничения из ARCHITECTURE.md
- Зависимости между требованиями

**Как проверить:** Попарное сравнение — нет ли взаимоисключающих формулировок? Нет ли требований, которые невозможно удовлетворить одновременно? Проверьте соответствие стеку и архитектуре.

**Почему:** Конфликтующие требования создают неразрешимые ситуации при реализации. Разработчик вынужден делать выбор без информации, что ведёт к техдолгу.

---

### Singular (5 pts)

**Определение:** Требование описывает одну атомарную задачу или аспект.

**Что собрать:**
- Декомпозицию требования на составные части
- Признаки составности: "и", "а также", "при этом", "одновременно"

**Как проверить:** Содержит ли требование несколько независимых аспектов? Можно ли реализовать его частично? Если да — разбить на отдельные требования.

**Почему:** Составные требования невозможно точно оценить по усилиям, протестировать точечно и отследить по статусу выполнения. Частичная реализация создаёт иллюзию прогресса.

---

### Feasible (5 pts)

**Определение:** Требование достижимо при заданных технических, временных и ресурсных ограничениях.

**Что собрать:**
- Технические ограничения (стек, инфраструктура, платформа)
- Доступные ресурсы (время, бюджет, экспертиза команды)
- Прецеденты реализации аналогичного в индустрии

**Как проверить:** Есть ли техническая возможность? Есть ли прецеденты? Достаточно ли ресурсов? Соответствует ли текущему стеку из ARCHITECTURE.md?

**Почему:** Недостижимые требования тратят время на проектирование нереализуемого. Обнаружение недостижимости на этапе реализации = потерянный sprint.

---

### Traceable (5 pts)

**Определение:** Требование можно проследить до бизнес-цели или потребности стейкхолдера.

**Что собрать:**
- Источник требования (стейкхолдер, документ, регуляция)
- Связь с бизнес-целью проекта
- Цепочку: потребность → требование → реализация → тест

**Как проверить:** Для каждого требования можно ответить: "Зачем это нужно? Кому? Какую проблему решает?" Нет чёткого ответа — трассировка отсутствует.

**Почему:** Без трассировки невозможно оценить ценность требования, приоритизировать изменения и обосновать решения при пересмотре scope.

---

### Verifiable (5 pts)

**Определение:** Выполнение требования можно объективно подтвердить через тестирование или инспекцию.

**Что собрать:**
- Критерии приёмки для каждого требования
- Метрики (время отклика, объём данных, процент покрытия)
- Тестовые сценарии или чек-листы проверок

**Как проверить:** Можно ли написать конкретный тест? Есть ли количественные критерии вместо "работает корректно"? Может ли QA однозначно подтвердить выполнение?

**Почему:** Невербицируемые требования невозможно подтвердить как выполненные. Это ведёт к бесконечным спорам о готовности и откладыванию релизов.

## Section 2: Requirement Set Integrity (20 pts)

Целостность набора требований как единого целого (IEEE 29148:2018, Clause 5.2.5).

| Criterion | Wt | Что проверить |
|---|---|---|
| Set Complete | 5 | Все функциональные области покрыты? Нет очевидных пробелов в сценариях? |
| Set Consistent | 5 | Требования не конфликтуют между собой? Нет взаимоисключающих условий? |
| No Duplication | 5 | Каждое требование описано ровно один раз? Нет пересекающихся формулировок? |
| Prioritized | 5 | Требования ранжированы (Must/Should/Could/Won't)? Этапы в порядке зависимости? |

---

## Section 3: Requirement Types Coverage (20 pts)

Покрытие типов требований (IEEE 29148:2018, Clause 5.3).

| Criterion | Wt | Что проверить |
|---|---|---|
| Functional | 5 | Описано ЧТО система делает: входы, выходы, поведение, переходы состояний? |
| Non-Functional | 5 | Описано КАК система работает: производительность, безопасность, UX, совместимость? |
| Constraints | 5 | Учтены ограничения: технологии, стандарты, регуляции, платформа, версионность? |
| Acceptance | 5 | Определены чёткие критерии приёмки для каждого этапа реализации? |

---

## Section 4: Implementation Readiness (20 pts)

Готовность требований к передаче в реализацию.

| Criterion | Wt | Что проверить |
|---|---|---|
| Decomposed | 5 | Требования разбиты на этапы с явными границами? Каждый этап автономен? |
| Actionable | 5 | Каждый этап содержит конкретные файлы, функции и чёткий критерий готовности? |
| Dependencies | 5 | Зависимости между этапами и модулями явно указаны? Порядок обоснован? |
| No Assumptions | 5 | Нет неявных допущений — все ограничения, решения и компромиссы документированы? |

---

## Scoring Rules

1. Каждый критерий: **0** (нет) / **3** (частично) / **5** (полностью)
2. Итого: сумма 20 критериев = 0–100 баллов
3. **Pass:** ≥85 баллов
4. **Fail:** переработать проваленные критерии, повторить валидацию

## Алгоритм валидации

1. Прочитать spec целиком
2. Для каждого требования оценить 8 атрибутов (Section 1)
3. Оценить целостность набора (Section 2)
4. Проверить покрытие типов требований (Section 3)
5. Оценить готовность к реализации (Section 4)
6. Подсчитать итоговый score
7. <85 — вывести проваленные критерии с рекомендациями
8. ≥85 — spec проходит валидацию
